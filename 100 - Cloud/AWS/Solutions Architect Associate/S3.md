# Amazon S3

> For foundational S3 concepts (objects, buckets basics, security overview), see [[100 - Cloud/AWS/Cloud Practitioner/S3|Cloud Practitioner: S3]].

## Buckets

S3 stores objects (files) in **buckets** (directories). Buckets are defined at the **region level**. S3 looks like a global service, but each bucket is created in a specific region.

### Naming

S3 uses a **shared global namespace** by default, meaning bucket names are unique across all regions and all accounts. An **account regional namespace** allows reuse of the same bucket name across regions.

**Naming constraints:**
- No uppercase, no underscores
- Must not be an IP address
- Must start with a lowercase letter or number
- Must not start with the prefix `xn--`
- Must not end with the suffix `-s3alias`

## Versioning

Versioning is enabled at the **bucket level**. When enabled, overwriting the same key creates a new version (1, 2, 3...).

**Best practice:** always enable versioning on buckets.
- Protects against unintended deletes (ability to restore a version)
- Easy rollback to a previous version

**Notes:**
- Files not versioned before enabling versioning get version `null`
- Suspending versioning does **not** delete previous versions; it just stops creating new ones

## Replication

Replication requires **versioning enabled on both source and destination buckets**.

| Type | Description |
|------|-------------|
| **Cross-Region Replication (CRR)** | Replicates to a bucket in a different region |
| **Same-Region Replication (SRR)** | Replicates to a bucket in the same region |

**Key details:**
- Buckets can be in **different AWS accounts**
- Copying is **asynchronous**
- Must give proper **IAM permissions** to S3

**Use cases:**
- **CRR:** compliance, lower latency access, replication across accounts
- **SRR:** log aggregation, live replication between production and test accounts

**Behavior after enabling replication:**
- Only **new objects** are replicated by default
- Existing objects can be replicated using **S3 Batch Replication** (also retries failed replications)
- **Delete markers** from source are optionally replicated to target
- Deletions with a **version ID** are **not** replicated (prevents malicious deletes)
- **No chaining:** if bucket 1 replicates to bucket 2, and bucket 2 replicates to bucket 3, objects from bucket 1 are **not** replicated to bucket 3

## Storage Classes

All classes share **99.999999999% (11 nines) durability**. Durability text is identical across classes; the differences are in availability, AZ count, retrieval speed, minimum duration, and cost.

### Comparison

| | Standard | Intelligent-Tiering | Express One Zone | Standard-IA | One Zone-IA | Glacier Instant | Glacier Flexible | Glacier Deep Archive |
|---|---|---|---|---|---|---|---|---|
| **Availability** | 99.99% | 99.9% | 99.95% | 99.9% | 99.5% | 99.9% | 99.99% | 99.99% |
| **Availability SLA** | 99.9% | 99% | 99.9% | 99% | 99% | 99% | 99.9% | 99.9% |
| **AZs** | >=3 | >=3 | 1 | >=3 | 1 | >=3 | >=3 | >=3 |
| **First byte latency** | ms | ms | single-digit ms | ms | ms | ms | min to hr | hr |
| **Min storage duration** | N/A | N/A | 1 hr | 30 days | 30 days | 90 days | 90 days | 180 days |
| **Retrieval charge** | none | none | per GB | per GB | per GB | per GB | per GB | per GB |
| **Lifecycle transitions** | yes | yes | no | yes | yes | yes | yes | yes |

### Standard
99.99% availability. Sustain 2 concurrent facility failures. Big data analytics, mobile/gaming, content distribution.

### Infrequent Access
For data accessed less often but requiring rapid retrieval when needed. Lower cost than Standard.

- **Standard-IA:** 99.9% availability, >=3 AZs. Disaster recovery, backups.
- **One Zone-IA:** 99.5% availability, single AZ. Data lost when AZ is destroyed. Secondary backups, recreatable data.

### Glacier (Archive)
Low-cost archiving/backup. Pricing: storage + retrieval cost.

- **Glacier Instant Retrieval:** millisecond retrieval, 90-day minimum. Data accessed once a quarter.
- **Glacier Flexible Retrieval:** Expedited (1-5 min), Standard (3-5 hr), Bulk (5-12 hr, free). 90-day minimum.
- **Glacier Deep Archive:** Standard (12 hr), Bulk (48 hr). 180-day minimum. Long-term regulatory retention.

### Intelligent-Tiering
Small monthly monitoring/auto-tiering fee. No retrieval charges. Moves objects automatically between tiers:

- **Frequent Access** (automatic, default)
- **Infrequent Access** (automatic, not accessed for 30 days)
- **Archive Instant Access** (automatic, not accessed for 90 days)
- **Archive Access** (optional, configurable 90-700+ days)
- **Deep Archive Access** (optional, configurable 180-700+ days)

### Express One Zone
High-performance, single-AZ storage class. Objects stored in a **Directory Bucket**.

- 100,000s requests/sec, single-digit ms latency
- Up to 10x better performance than Standard (50% lower costs)
- Co-locate storage and compute in the same AZ to reduce latency
- Use cases: latency-sensitive apps, AI/ML training, financial modeling, media processing, HPC
- Integrations: SageMaker Model Training, Athena, EMR, Glue

## Lifecycle Rules

Lifecycle rules transition objects between storage classes or expire (delete) them based on age. Rules can target **current versions** or **noncurrent versions** independently.

### Scenario 1: Thumbnails + Source Images
Application creates thumbnails from profile photos. Thumbnails are easily recreatable, kept 60 days. Source images need immediate access for 60 days, then can wait up to 6 hours.

**Design:**
- Source images: **Standard** with lifecycle rule to transition to **Glacier Flexible Retrieval** after 60 days (Standard retrieval = 3-5 hours)
- Thumbnails: **One Zone-IA** (recreatable data, single AZ is fine) with lifecycle rule to **expire** (delete) after 60 days

### Scenario 2: Recoverable Deletes
Company rule: deleted objects recoverable immediately for 30 days, then recoverable within 48 hours for up to 365 days.

**Design:**
- Enable **S3 Versioning** so deletes create a delete marker (objects are hidden, not destroyed, and can be recovered)
- Transition **noncurrent versions** to **Standard-IA** after 0 days (immediate, for the first 30 days of cheap storage)
- Transition **noncurrent versions** to **Glacier Deep Archive** after 30 days (Bulk retrieval = 48 hours, covers days 31-365)

## `Object Encryption`

Four encryption methods for S3 objects:

| Method | Key Management | Use Case |
|--------|----------------|----------|
| **SSE-S3** | AWS-managed keys | Default for new buckets/objects. Header: `x-amz-server-side-encryption: AES256` |
| **SSE-KMS** | AWS KMS | User control + CloudTrail audit. Header: `x-amz-server-side-encryption: aws:kms`. Subject to KMS rate limits (5500-30000 req/s by region) |
| **SSE-C** | Customer-provided | Keys never stored by AWS. HTTPS required. Key in HTTP headers per request |
| **Client-Side** | Customer fully manages | Encrypt before upload, decrypt after download using S3 Client-Side Encryption Library |

**SSE-KMS APIs:** `GenerateDataKey` (upload), `Decrypt` (download). Request quota increase via Service Quotas Console if needed.

## `CORS` (Cross-Origin Resource Sharing)

**Origin** = scheme + host + port (e.g. `https://www.example.com`).

When a client makes cross-origin requests to your S3 bucket, enable CORS headers (`Access-Control-Allow-Origin`). Can allow specific origins or `*` (all). Popular exam question.

## `MFA Delete`

Requires MFA code to:
- Permanently delete an object version
- Suspend versioning on the bucket

Does **not** require MFA to:
- Enable versioning
- List deleted versions

**Requirements:** versioning must be enabled. Only bucket owner (root) can enable/disable MFA Delete.

## `Pre-Signed URLs`

Generate via S3 Console, CLI, or SDK. URL inherits permissions of the generating user for GET/PUT.

**Expiration:**
- Console: 1 min to 720 mins (12 hours)
- CLI: `--expires-in` parameter (default 3600s, max 604800s ~ 7 days)

**Use cases:** temporary access for logged-in users, dynamic file sharing, time-limited uploads.

## `Glacier Vault Lock`

WORM (Write Once Read Many) model. Create vault lock policy, then lock it (cannot be changed or deleted). For compliance and data retention.

## `Object Lock`

Requires **versioning enabled**. WORM model that blocks object version deletion for a specified time.

| Mode | Behavior |
|------|----------|
| **Compliance** | No user (including root) can overwrite/delete or change retention. Retention periods cannot be shortened |
| **Governance** | Most users blocked; special permissions can alter retention or delete |

**Retention Period:** protect object for fixed duration (can be extended).

**Legal Hold:** protect indefinitely, independent of retention. Placed/removed using `s3:PutObjectLegalHold` permission.

## `Access Points`

Simplify security management at scale. Each access point has:
- Own DNS name (Internet or VPC origin)
- Access point policy (similar to bucket policy)

Can restrict access to VPC-only via VPC Endpoint (Gateway or Interface). VPC Endpoint Policy must allow access to target bucket and access point.

## `Object Lambda`

Use Lambda functions to transform objects before retrieval. Create S3 Access Point + S3 Object Lambda Access Point on top of one bucket.

**Use cases:** redact PII for analytics, convert XML to JSON, resize/watermark images on-the-fly based on caller.

## `Requester Pays`

By default, bucket owners pay for all storage and data transfer costs. With **Requester Pays** buckets, the **requester** pays for requests and data download instead.

- Helpful when sharing large datasets with other accounts
- Requester must be authenticated in AWS (cannot be anonymous)

## S3 as a Key-Value Store

S3 is fundamentally a **key-value store**. The **key** is the full path of the object in the bucket (e.g., `my-bucket/folder/file.txt`), and the **value** is the object itself.

> [!example] Exam question
> You have a set of files, 100MB each, that you want to store in a reliable and durable key-value store. Which AWS service?
> **Answer: Amazon S3** (not DynamoDB, which has a 400KB item limit; not Aurora; not ElastiCache).
